The proof

a real docker compose up run, not fixtures

150 seeded customers, four months of transaction history, four batch jobs run against a live Postgres and Redpanda. Two of the numbers below aren't the ones this run was looking for - they're bugs the run found by itself.

Bug #1 - a session that closed before the log line read it

The Kafka consumer loaded a Notification outside any transaction, then read its lazily-loaded Customer to build the mock delivery message. Every message failed with LazyInitializationException on the first live run - correct Hibernate behavior; the session was already gone. Fixed with one @Transactional on the listener.

Bug #2 - 12 notifications that will never arrive, and that's the point

After the fix, only 30 of 42 notification requests reached the consumer. The other 12 were published before a Redpanda address fix, while the producer's .send() silently failed - the exact gap the code's own comment calls out: a database write with no delivery guarantee tied to it. Nothing here was patched over; those 12 rows are still sitting in REQUESTED in the seeded database today.

Three decisions, not defaults

Java 11 and Spring Boot 2.7

The last release before the jump - the version pair a lot of real systems are still on, not by recent choice but because nobody's migrated yet. ddl-auto: update owns the schema instead of Flyway, for the same reason.

application.yml

Matching by attribute, not by ID

An external bank statement and this system's invoices never shared a database key, so reconciliation can't index its way to a match. It scans - O(lines × invoices) - because that's genuinely the only option once there's no clean key to look up by.

ReconciliationMatchJob.java

No delivery guarantee - and it showed

Notification requests are written to the database, then published to Kafka separately - not atomically. The first live run left 12 of 42 requests stranded in REQUESTED forever, a live instance of the exact gap the code predicted.
